2026 Paris OpenAI Privacy Hackathon

Necessity Certificate

AI needs context, not identity. We turn a raw customer record into the smallest purpose-specific facts an AI task needs, with evidence for every omission or transformation.

The problem

How do we ensure privacy by design, not privacy by reaction?

Most privacy tooling today

Detects, masks, or redacts personal data after it has already reached the AI system boundary.

What looks personal?

What we do instead

Test, upfront and by construction, whether the declared AI task actually needs a given field at all.

Does this task need this data?

Step 0 — Counterfactual necessity test

Every field earns its place with evidence, not guesswork

16 synthetic support tickets, one fixed routing model. Each field is removed, one at a time, and the task is re-run.

Step A — Differential-privacy-aware SQL minimization

From necessity evidence to enforced, encrypted SQL

AI-facing view — fail-closed by default

CREATE VIEW support_tickets_ai_view AS
SELECT
    id,
    issue_description,
    product_area
FROM support_tickets;

Only necessity-proven columns. Untested columns (e.g. support_notes) are blocked too.

Base table — PII encrypted at rest

CREATE TABLE support_tickets_secure (
    id TEXT PRIMARY KEY,
    issue_description TEXT,
    product_area TEXT,
    name_enc BYTEA,      -- pgp_sym_encrypt
    email_enc BYTEA,     -- pgp_sym_encrypt
    account_id_enc BYTEA -- pgp_sym_encrypt
);

Blocked-but-needed PII never leaves the DB in plaintext, never reaches the model.
